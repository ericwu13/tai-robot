## EXE 變更 EXE changes

- **#217**（squash `754ddf79`）：儀表板可將以 v2.19.11 啟動的 headless bot 在模擬與全自動（實單）之間切換。儀表板寫入 `mode_request.json`，bot 回覆於 `mode_request_result.json`（檢查中／已切換／被拒與原因）。切到全自動需全部成立：全域 `allow_live_override: true`（儀表板與 bot 兩端都檢查）；該 bot 在 `dashboard_auto_opt_in` 中設為 `true`（預設全部關閉）；輸入 bot 名稱與「實單」；每日虧損上限為 1 到上限之間的整數，上限為 `MAX_MODE_SWITCH_LOSS_LIMIT_NTD` = 新台幣 20,000（限制的是本次切換設定的每日虧損上限，`mode_switch_max_loss_ntd` 只能逐 bot 調低）；請求超過 60 秒（或時間超前 5 秒以上）即拒絕；bot 須為運作中、無模擬持倉、無待成交委託、非重播／重載、交易防護未暫停、連線未封鎖；並即時查詢實單未平倉（任何實單部位、查詢失敗或逾時都拒絕）。通過後先設定虧損上限再切換。被拒的全自動請求會寫入稽核紀錄與日誌，並發 Discord 通知（每 5 分鐘最多一次）。切回模擬也走同一通道，否則沿用 `mode_override.json`。#207 的 `mode_override.json` 拒絕不變。
  **#217** (squash `754ddf79`): the dashboard can switch a headless bot started on v2.19.11 between paper and auto (real orders). The dashboard writes `mode_request.json`; the bot answers in `mode_request_result.json` (checking / switched / refused with reason). Auto requires all of: global `allow_live_override: true` (checked by both the dashboard and the bot); that bot set to `true` in `dashboard_auto_opt_in` (all off by default); the bot name and 「實單」 typed to confirm; a daily loss limit that is an integer from 1 up to the cap, `MAX_MODE_SWITCH_LOSS_LIMIT_NTD` = NT$20,000 (it caps the daily loss limit set by this switch; `mode_switch_max_loss_ntd` can only lower it per bot); a request no older than 60 s (or no more than 5 s in the future); the bot running with no sim position, no pending fill, no replay/reload, guard not halted/paused and link not blocked; and a fresh real open-interest query (any real position, query error or timeout refuses). On success the loss limit is set before the switch. A refused auto request is audited, logged, and sent as a Discord notice (at most one per 5 minutes). Paper uses the same channel, else the legacy `mode_override.json`. #207's `mode_override.json` refusal is unchanged.
- **#208**（squash `fb51ddcc`）：regime 存檔（`regime_state.json`、placeholder 狀態、歷史 CSV 的原子寫入，以及 manager 的 `last_features` 與「建議已執行」寫入）改為遇到 `PermissionError` 時重試，最多 4 次、退避 5／10／20 毫秒（共約 35 毫秒），與心跳寫入相同。Windows 上監控或儀表板正在讀檔時，`os.replace` 會失敗；先前會讓 regime 存檔出錯，或使「建議已執行」未保存而在重啟後再次觸發。其他錯誤仍立即拋出；檔案被佔用超過重試時間仍會失敗。舊版歷史 CSV 遷移的改名（`regime_history_legacy.csv`）不變，仍為直接 `os.replace`。
  **#208** (squash `fb51ddcc`): regime store writes (`regime_state.json`, the placeholder state, the history CSV atomic writes, and the manager's `last_features` and recommendation-executed writes) now retry `PermissionError` up to 4 attempts with 5/10/20 ms backoff (about 35 ms total), the same budget as the heartbeat writer. On Windows `os.replace` fails while the monitor or dashboard has the file open; before, that could fail a regime save, or leave a recommendation marked not executed so a restart re-armed it. Any other error still raises at once, and a handle held longer than the retry budget still fails. The legacy history CSV migration rename (to `regime_history_legacy.csv`) is unchanged and still a plain `os.replace`.
- **#207**（squash `6f69ff15`，實單安全防護 real-money safety guard）：headless bot 的 `mode_override.json` 只接受 `"paper"`。要求 `auto`、`real`、`semi_auto`、其他字串或非字串值（以及無效 JSON）一律拒絕，即使 `allow_live_override` 為 true；目前模式不變，檔案改名為 `mode_override.json.refused`（舊的 refused 移為 `.refused.N`；改名失敗則刪除，再失敗則以指紋忽略該檔直到其變更）。操作者看到的是 bot 日誌與狀態列的警告 `[MODE] headless refused mode_override.json trading_mode=... staying on '<mode>' (file consumed)`；不發 Discord／警報、bot 不退出、無退出碼。`deploy --mode auto` 不受影響。GUI 部署（origin 為 gui 且非 headless）的熱切換不變；缺少 origin 時預設啟用防護（fail closed）。headless 驅動在 `_deploy` 的 try 與 finally 都會啟用防護。
  **#207** (squash `6f69ff15`, real-money safety guard): a headless bot's `mode_override.json` accepts only `"paper"`. `auto`, `real`, `semi_auto`, any other string, any non-string value, and invalid JSON are refused, even with `allow_live_override: true`. The mode stays unchanged and the file is renamed to `mode_override.json.refused` (an older one moves to `.refused.N`; if the rename fails it is deleted; if that fails the exact file is fingerprinted and ignored until it changes). The operator sees a warning in the bot log and status line: `[MODE] headless refused mode_override.json trading_mode=... staying on '<mode>' (file consumed)`. There is no Discord alert, no exit, and no exit code. `deploy --mode auto` is unchanged. GUI deploys (origin gui and not headless) keep file hot-swap as before; a missing origin arms the guard (fail closed). The headless driver arms it in both the try and the finally of `_deploy`.
- **#222**（squash `d77d8aef`，緩解 #219）：回報（reply）連線靜默時的輪詢與新進場暫停。v2.19.9 起回報事件可能未送達 Python，連線狀態機看不到回報斷線、也不會送 `ConnectByID`。現每 60 秒及每次 3003 輪詢 `IsConnectedByID`：回傳 `0` 時暫停新的實單進場（沿用 `orders_paused`／`link_entries_blocked`），並依 5、10、30、60 秒退避送 `ConnectByID`，10 次未恢復即再發警告並停止重試；回傳 `1` 時標記回報 READY 並解除該暫停。登入、偵測到斷線或送出實單後 60 秒內沒有任何 OnConnect／OnComplete／OnNewData，會發 `REPLY CHANNEL SILENT` 警告（不暫停）。出場與平倉一律允許。不呼叫登出。GUI 與 headless 共用。另增加回報事件診斷日誌（不含帳號資料）。根因（事件分派）仍待查。
  **#222** (squash `d77d8aef`, mitigates #219): poll a silent reply link and pause new entries. Since v2.19.9 reply events may not reach Python, so the link machine never saw a reply drop or sent `ConnectByID`. `IsConnectedByID` is now polled every 60 s and on each 3003. `0` pauses new real entries (the existing `orders_paused` / `link_entries_blocked` path) and sends `ConnectByID` with 5/10/30/60 s backoff; after 10 attempts without recovery it alerts again and stops retrying. `1` marks the reply READY and lifts that pause. A `REPLY CHANNEL SILENT` alert fires if no OnConnect/OnComplete/OnNewData arrives within 60 s of login, a detected drop, or a real order (alert only, no pause). Exits and closes are always allowed. Logout is never called. GUI and headless share it. Adds reply-sink diagnostics to the bot log (no account data). The event-dispatch root cause is still open.
- **#221**（squash `24e562fa`）：headless `deploy` 在取得鎖後寫入 `headless.json`（pid 與程序建立時間），結束時移除；GUI 部署會刪除殘留的 `headless.json`。儀表板只有在此標記有效（pid 與鎖相符、程序確實存活、可讀到建立時間時須相符）時才啟用「停止」與「改為模擬」，否則按鈕停用並顯示「GUI 機器人，請在程式中操作」，且不寫入 `STOP`／`CONTROL`／`mode_override.json`。控制日誌預設改為安裝目錄下的 `dashboard_control_log.csv`。GUI 即時迴圈仍不讀 `STOP`。
  **#221** (squash `24e562fa`): a headless `deploy` writes `headless.json` (pid and process start time) after acquiring the lock and removes it on exit; a GUI deploy deletes a stale `headless.json`. The dashboard enables 停止 (stop) and 改為模擬 (switch to paper) only when that marker is valid (pid matches the lock, the process is strictly alive, start time matches when it can be read); otherwise the buttons are disabled with "GUI 機器人，請在程式中操作" and nothing is written (`STOP`, `CONTROL`, `mode_override.json`). The control log now defaults to `dashboard_control_log.csv` in the install directory. The GUI live loop still does not poll `STOP`.

## 風險 Risks

- **#217 實單切換**：這是新的實單升級途徑。bot 端會重新檢查全域開關、逐 bot 允許、虧損上限、時效與帳戶狀態，但「bot 名稱／實單」確認只由儀表板檢查；能寫入 bot 資料夾的程式，在已開啟的 bot 上可直接要求切換。開啟 `allow_live_override` 也會讓 GUI 的 `mode_override.json` 可切到 auto（headless 仍由 #207 拒絕）。 / **#217 real-money switch**: this is a new path into real orders. The bot re-checks the global switch, per-bot opt-in, loss cap, request age and account state, but the bot-name/「實單」 confirmation is checked only by the dashboard; anything that can write to a bot's folder can request the switch on an opted-in bot. Turning on `allow_live_override` also lets a GUI bot's `mode_override.json` switch to auto (headless still refused by #207).
- **#208**：重試只涵蓋短暫的讀取（約 35 毫秒）；若其他程式長時間佔用 regime 檔案，存檔仍會失敗，行為與 v2.19.10 相同。 / **#208**: the retry only covers brief reads (about 35 ms); a process holding a regime file longer still makes the save fail, as in v2.19.10.
- **#207**：之前以 `mode_override.json` 將 headless bot 升為 auto 的流程不再有效（只能以 `deploy --mode auto` 重新部署）；拒絕只寫日誌、不發警報，需看日誌或 `.refused` 檔確認。 / **#207**: any workflow that promoted a headless bot to auto by dropping `mode_override.json` stops working (redeploy with `deploy --mode auto` instead). A refusal only logs, with no alert, so check the bot log or the `.refused` file.
- **#222 暫停進場**：若 `IsConnectedByID` 誤報 0，或 10 次重試後仍未恢復，新進場會持續暫停（出場仍允許），直到回報恢復或手動處理；此為緩解，根因未解。 / **#222 entry pause**: a false `0`, or a link that stays down after 10 attempts, keeps new entries paused (exits still allowed) until the reply recovers or someone intervenes. It is a mitigation; the root cause is open.
- **#222 警告量**：靜默監測可能在回報正常但事件未送達時發出警告。 / **#222 alert noise**: the silent-sink watchdog can alert when the link is up but events are not delivered.
- **#221 控制停用**：仍在舊版、或升級後尚未重啟的 headless bot 沒有 `headless.json`，儀表板停止／改為模擬會維持停用，直到以新 EXE 重啟。若讀不到程序建立時間（含存取被拒或其他系統錯誤，皆回傳空值），略過時間比對，仍以鎖 pid 檢查為準；讀取時發生未預期的例外則維持停用。 / **#221 controls disabled**: headless bots on older builds, or not restarted after the swap, have no `headless.json`, so dashboard stop/paper stay disabled until they restart on the new EXE. If no process start time is returned (access denied and other OS errors also return none), the time check is skipped and the lock-pid check stands; an unexpected exception during the read keeps the controls disabled.
